# 1. Chat Format and Roles

## 1.1 What is Chat Format?

Chat format is a structured way of sending messages to an LLM through an API.

Instead of sending plain text, we send messages with specific roles so the model can understand:
- Who is speaking?
- What is being said?
- What instructions should be followed?
- What is the conversation history?

A typical chat request contains an array of messages.

Example:

```json
{
  "messages": [
    {
      "role": "system",
      "content": "You are a helpful assistant."
    },
    {
      "role": "user",
      "content": "What is JavaScript?"
    }
  ]
}
```

## 1.2 Different Message Roles

Each message has a role that identifies its source or purpose.

### 1. System Role

- Provides high-level instructions to the model.
- Defines the model's behavior, personality, rules and response style.
- Usually remains consistent throughout a conversation.

Example:

```json
{
  "role": "system",
  "content": "You are a helpful programming tutor. Explain concepts using simple language."
}
```

### 2. User Role

- Contains the input or question provided by the user.
- Represents what the user wants the model to do.

Example:

```json
{
  "role": "user",
  "content": "Explain React hooks."
}
```

### 3. Assistant Role

- Represents messages generated by the AI model.
- Contains the model's responses.
- Previous assistant messages can be included in subsequent API requests as conversation history.

Example:

```json
{
  "role": "assistant",
  "content": "React hooks are functions that let you use React features in functional components."
}
```

**Note:** Some APIs also support additional roles, such as `developer` and `tool`. Their exact formats depend on the provider.

## 1.3 How Does a Chat Conversation Work?

A conversation consists of multiple messages exchanged between the user and the assistant.

Example:

```json
[
  {
    "role": "system",
    "content": "You are a helpful assistant."
  },
  {
    "role": "user",
    "content": "What is JavaScript?"
  },
  {
    "role": "assistant",
    "content": "JavaScript is a programming language used to build interactive applications."
  },
  {
    "role": "user",
    "content": "Where is it used?"
  }
]
```

The model receives the conversation messages and generates the next assistant response.

The conversation history helps the model understand previous questions and maintain context.

## 1.4 What is Multi-turn Conversation?

A multi-turn conversation is a conversation involving multiple exchanges between the user and the assistant.

For example:

- Turn 1: User asks, "What is JavaScript?"
- Turn 2: Assistant explains JavaScript.
- Turn 3: User asks, "Where is it used?"
- Turn 4: Assistant explains its applications.

The second user question depends on the previous conversation.

To maintain this context, the application generally sends relevant previous messages along with the latest user message in the next API request.

**Important:** Most LLM APIs do not automatically remember previous API requests. Your application needs to maintain and send conversation history, unless you use a provider's specific conversation or state-management feature.

## 1.5 How Does an LLM API Request Work?

A typical API interaction follows these steps:

1. User sends a message through the frontend.
2. Frontend sends the message to the backend.
3. Backend constructs the conversation messages, including relevant history and instructions.
4. Backend sends an API request to the LLM provider.
5. LLM processes the messages and generates a response.
6. Backend receives the response.
7. Backend sends the response to the frontend.
8. Frontend displays the assistant's response.

## 1.6 What is an Official SDK?

SDK stands for Software Development Kit.

An official SDK is a library provided by an API provider to make interacting with its API easier.

For example:
- OpenAI SDK
- Google Gen AI SDK
- Anthropic SDK

Instead of manually constructing HTTP requests, an SDK provides ready-made methods to communicate with the provider.

## 1.7 Official SDK vs Plain Fetch

### Official SDK

- Uses a provider-maintained JavaScript library.
- Provides methods for making API requests.
- Often simplifies authentication, request construction, streaming and error handling.
- Usually provides TypeScript types.

### Plain Fetch

- Uses JavaScript's built-in `fetch()` function.
- Sends HTTP requests directly to the provider's API endpoint.
- Requires manually configuring headers, authentication and request bodies.
- Gives more direct control over HTTP communication.

Both approaches communicate with the same underlying API.

Example using plain fetch:

```javascript
const response = await fetch(API_URL, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": `Bearer ${API_KEY}`
  },
  body: JSON.stringify({
    messages: [
      {
        role: "user",
        content: "What is JavaScript?"
      }
    ]
  })
});

const data = await response.json();
```

Note: `API_URL`, request structure and authentication headers depend on the provider. This is an illustrative example, not a universal API request.

## 1.8 Different LLM Providers

Different providers offer APIs to interact with their models.

| Provider | Example models |
|---|---|
| OpenAI | GPT models |
| Google | Gemini models |
| Anthropic | Claude models |

All three support conversational interactions, but their API request formats, SDK methods and message structures are not necessarily identical.

For example:
- OpenAI uses message-based conversation formats.
- Anthropic uses a top-level `system` parameter and a messages array.
- Gemini uses its own `contents` and `parts` structure, with system instructions handled separately.

Therefore, you should understand the underlying chat concepts before learning each provider's API.

---

## Key Takeaways

1. Chat format structures messages sent to an LLM.
2. Roles identify who is speaking and the purpose of a message.
3. System messages provide instructions, user messages provide input, and assistant messages contain AI responses.
4. Multi-turn conversations require maintaining relevant conversation history.
5. LLM APIs generally do not remember previous independent requests automatically.
6. Official SDKs simplify API communication, while plain fetch gives direct HTTP control.
7. Different providers can use different API formats even though the underlying conversational concepts are similar.
